# 10 · 多场次（多场竞赛）设计

> 目标：让平台同时承载**多场竞赛**，各自独立的赛题、提交、榜单、队伍。

## 1. 为什么要这一层

在此之前平台从数据模型到路由到模板都硬编码「只有一场比赛」：

- 赛题是模块级常量（`problems.py` / `riscv_problems.py`），没有场次维度；
- `Submission` 只有 `team_name` / `problem_id`，`Team` / `TeamMember` 全局唯一（每人一队）；
- `standings.build_standings()` 把**所有**提交混在一起排名；
- `stage` 查询参数是历史遗留、从不参与过滤。

## 2. 概念

**场次（Contest）= 隔离单位。** 赛题 + 提交 + 榜单 + 队伍都按场次隔离；
**用户账号（User）保持全局**——一个人可以在不同场次各加入一支队伍。

> Stage 1 与 Stage 2 属于**同一场竞赛**（线上赛 + 线下决赛），
> 它们是同一场次内的阶段，不是两个场次。**当前处在哪个阶段由日期推出**，拼进状态显示
> （如「进行中 · Stage 1」），页面上没有独立的「阶段」标签。

## 3. 场次注册表 `contests.py`

**用代码注册**（不做后台管理界面）。加一场 = 加一条 `Contest(...)` 并重启。

全局**题册**（`problems.PROBLEMS` 展示元数据 + `riscv_problems.EVAL_SPECS` 评测规格）保持不动，
场次只负责两件事：

1. **挑选**本场试卷：`problem_ids`（有序；空 = 整本题册）；
2. 可选地**局部覆盖**某题规格：`eval_overrides` / `baseline_file` / `seeds`。

### 字段

| 字段 | 含义 |
|---|---|
| `slug` | URL 段（`/c/<slug>/...`），全局唯一、发布后别改（会断链） |
| `title` / `short_title` | 全称 / 短名（导航、切换器） |
| `status` | `upcoming` / `running` / `ended`。**进入闸**（`_guard_contest_entry`）：①**未开始进不去**（`is_enterable`）；②**需报名但未报名也看不到内容**（`requires_registration` + `is_enrolled`）——未通过一律 403（题面/榜单/API 都不放）。**参加闸**（`is_open`）：只有进行中能组队/入队与提交。已结束可进但只读 |
| `start_at` / `end_at` | **比赛**起止（朴素 UTC，展示时转 UTC+8，可为 None） |
| `registration_start` / `registration_end` | **报名**起止（仅需报名的场次用）。配了就**按日期开关报名**，没配则按状态兜底 |
| `problem_ids` | 本场试卷（有序）；空 = 全部 |
| `default` | 默认场次（旧 URL 的落点），全局恰一个 |
| `requires_registration` | 是否需要**个人报名**（见下）：True → 未报名**看不到内容**、不能建队/入队 |
| `registration_code` | 报名**邀请码**：需报名的场次必配，报名时要填对（未配则拒绝报名，fail closed） |
| `stages` | 场次内的**阶段**（`Stage(label, start_at, end_at)` 元组）：赛程面板逐段列出，且 `current_stage`/`status_display` 按日期推出「当前阶段」 |
| `eval_overrides` | `{题目id: {字段: 值}}` 局部覆盖该题评测规格 |
| `baseline_file` | 本场默认 baseline 路径（相对仓库根） |
| `seeds` | 本场官方评测种子（覆盖 `config.EVAL_SEEDS`） |

### 报名（可选）

有的场次需要报名、有的不需要，由 `requires_registration` 决定：

- **个人报名**（`enrollments` 表，`(user_id, contest)` 唯一）——先各自报名，再组队。
- 报名**需要邀请码**（`registration_code`）：填错或没配一律拒绝。邀请码由主办方分发，不在页面上显示。
- 需报名的场次里，**未报名者看不到任何内容**（整场 403，含匿名），且**不能建队/入队**
  （前者在进入闸、后者在 `_join_gate`），因此也不能提交。报名/取消报名接口是进入闸的**例外**。
- **已结束的场次对所有人公开**（归档回看）：`requires_enrollment_to_view` 对 `ended` 返回 False，
  报名闸不生效；目录页把它标成「已结束 · 公开」。
- **报名窗口**：配了 `registration_start/end` 就按日期；没配则按状态（未开始 + 进行中可报）。
  **赛程**（报名起止 + 比赛起止）显示在右栏「赛程」面板，UTC+8，未设置显示「—」。未开始的场次虽然进不去（`is_enterable` 为
  False），但**报名接口例外放行**——否则开赛前没法报名。报名入口在**赛事目录页 `/`**。
- 可**取消报名**，但已有队伍时须先退队。
- **赛事目录页**逐场标注 `无需报名` / `需报名` / `已报名`，并给报名/取消按钮。
- 无需报名的场次保持原行为（建队/入队即参赛）。

### 「同一道题、不同数据」

这正是 `eval_overrides` / `baseline_file` 的用途：两场共用 add/matmul/reducesum，
但各自用不同 baseline 与参考解——**无需复制整份 spec**，只覆盖变化的字段。

### 关键实现约束

`get_eval_spec(problem_id, contest)` 的合并结果**按 `(slug, problem_id)` 缓存**。
原因：`evaluator.py` 会往 spec 上挂 `_baselines`（读一次 baseline 缓存住）——
两场若共用同一个 dict，一个场次的 baseline 会**串到另一场**去。

`contest=None` → 默认场次，因此评测链路的旧调用点不改也能保持等价。

## 4. 数据模型与迁移

```python
Submission.contest           # 本提交所属场次
Team.contest                 # 队伍所属场次；队名**仅在**本场唯一 UNIQUE(contest,name)
TeamMember.contest           # 成员关系所属场次；UNIQUE(user_id,contest) = 每人每场限一队
User.memberships (一对多)     # 一个用户在多场各有一条成员关系
User.team_in(slug) / membership_in(slug)
```

`Team.invite_code` 仍**全局唯一**；入队时额外校验 `team.contest == 当前场次`，
防止拿别场的码串场入队。

**配额与限流都按「人 · 场次」计**：

- **每日配额 `DAILY_QUOTA` 按人计**——靠 `Submission.user_id`（提交人）统计，**换队不刷新额度**，
  堵掉「刷满 → 退队 → 换队名 → 又有额度」。老提交没有 `user_id`，不计入任何人。
- `SubmitThrottle`（提交间隔）按 `(user_id, contest)` 计时：在 A 场刚交完，B 场不受影响。
- **每人每场每天只能退队一次**（`team_leave_log` 只增流水，05:00 重置）——防止反复退队腾挪。
  限的是「退」，入队/建队不限。

### 迁移

`db.create_all()` 只建缺失的表、**不会 ALTER 已有表**（见 `models.py` 的 SubmitThrottle 注释与 docs/08）；
而本次要把 `teams.name` 的全局 UNIQUE 改成复合约束——**SQLite 只能重建表**。
所以线上库必须显式迁移：

```bash
.venv/bin/python tools/migrate_multicontest.py            # 只打印计划（dry-run）
.venv/bin/python tools/migrate_multicontest.py --apply    # 先自动备份，再迁移
```

- `--apply` 前**自动备份**到 `<db>.bak-<时间戳>`；
- 单事务 + `PRAGMA foreign_keys=OFF`；**迁移前后逐表行数必须一致**，否则回滚并非零退出；
- **幂等**：已迁移的库再跑只报告「无需改动」。

新库（测试 / 新部署）由 `create_all()` 直接得到新 schema，无需跑脚本。

## 5. URL 与路由

**所有场次相关的页面 / 片段 / 队伍 / API 都在 `/c/<slug>/` 下**：

```
/c/<slug>/                首页
/c/<slug>/problems[ /<pid>]
/c/<slug>/standings        /c/<slug>/frag/standings
/c/<slug>/submit           /c/<slug>/result/<id>      /c/<slug>/help
/c/<slug>/team[/join|/create|/leave|/restore|/reset-code|/transfer]
/c/<slug>/api/problems     /c/<slug>/api/submit      /c/<slug>/api/result/<id>
/c/<slug>/api/leaderboard/<pid>                       /c/<slug>/api/me  /c/<slug>/api/team*
```

`g.contest` 由蓝图的 `url_value_preprocessor` 从 `slug` 解析；未知 slug → 404。

**账号相关**（`/login`、`/register`、`/logout`、`/forgot-password`、`/reset-password`、`/api/auth/*`）
保持**全局**——账号跨场次。

**最外层 = 场次目录**：`/`（与 `/contests` 同页）列出全部场次，先选赛事再进门。
顶栏第一项「赛事」与品牌名都指向这里；进了某场后，场次内的首页是 `/c/<slug>/`。

**旧 URL 兼容**：

- 旧**页面**路径（`/problems*`、`/standings`、`/help`、`/result/<id>`、`/team*`）→ **302** 到默认场次；
- 旧 **`/submit`（含 POST）→ 307**，保住方法与请求体；
- 旧 **`/api/*` 原地委派**给默认场次（**不**重定向，免得打断不跟随重定向的 JSON 客户端）。

> 注：`/` 以前是「默认场次首页」，现在改成目录页；`/c/<slug>/` 才是场次首页。
> 所以静态导出里根 `index.html` = 目录，场次首页叫 `index-<slug>.html`。

导航/品牌条里有场次切换器，可从任一场次内直接跳到别场。

## 6. 模板与上下文

上下文处理器统一注入，模板源码几乎不用改：

```python
@app.context_processor
def inject_context():
    c = getattr(g, 'contest', None) or default_contest()
    return {'current_user': current_user(), 'contest': c, 'contests': all_contests(),
            'eval_spec': lambda pid: get_eval_spec(pid, c), 'eval_specs': specs_for(c), ...}
```

模板里调的 `eval_spec(p.id)` 由此**自动绑定当前场次**。其余改动只是给 `url_for` 补
`slug=contest.slug`，并把硬编码的「Stage 1」换成 `contest.status_display`。

`tests/test_contests.py` 覆盖：规格按场次取且同题可不同、全局题册不被污染、
提交/榜单严格隔离、一个用户多场各一队、队名跨场重名、邀请码不串场、

`run_evaluation(..., contest=None)` 与 `get_eval_spec(pid, contest=None)` 的默认参数，
让 `test_eval_*` / `test_scoring_*` **原样通过**（评测链路未被污染的证据）。

## 9. 已知边界

- 评测 worker 与 CLI 工具**没有请求上下文**，所以队伍一律走显式的
  `user.team_in(slug)`，**没有**读 `g.contest` 的 `user.team` 属性（那会静默取错场次）。
- 配额与提交间隔都按「人 · 场次」计；场次之间不共享额度（见 §4）。
- 成绩按**队名**记账（`submission.team_name`），**不随人迁移**：换队后新队不继承你在旧队的成绩。
- 队长不能踢人；队名不能改；两队不能合并。
- 场次试卷若在产生提交之后被改（增删题 id），历史提交可能算不出规格——
  属于配置变更的正常后果，进场前把 `problem_ids` 定下来。
