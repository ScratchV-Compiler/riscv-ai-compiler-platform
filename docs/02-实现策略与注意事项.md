## 一、实现策略

### 1.1 总体策略

1. **契约先行（contract-first）**：先把 JSON API 与 `/frag/*` 片段路由的字段冻结成一张表，前端与后端各自按表开发，避免返工。
2. **Mock 驱动并行**：后端（尤其身份/评测）未就绪前，前端用本地 mock JSON 开发，字段与契约表逐字对齐。
3. **小步验证**：每完成一个页面，立刻起服务用 Playwright MCP 截图 + 查 console/network，通过后再做下一页。
4. **零构建链**：htmx / Alpine / Bootstrap 全部 CDN 锁版本，禁止引入 Node/React/Vite。

### 1.2 分阶段路线（贴合后端现实）

平台初始状态**跑不起来**（`app.py` 未 import time、`tasks.py` 未 import app/json、缺 `/result` 路由、`to_dict` 缺 `details`），因此实现顺序定为后端解阻优先，否则前端无从联调。**该 4 项已在 P0 修复**（见 `docs/03` 第二章）。

| 阶段 | 目标 | 交付物 | 退出门槛 |
|---|---|---|---|
| **P0 解阻 + 契约冻结** | 修 4 个阻断 bug；冻结 API/片段契约 | 可跑通的空壳服务 + 契约表 | `POST /api/submit` 能建记录；`/api/result` 返回含 `details` |
| **P1 公共页** | 首页 / 赛题 / 排行榜 / 帮助 | 只读页面 + mock 榜单 | 桌面+移动截图无溢出、无 console 错误 |
| **P2 身份与组队** | 注册 / 登录 / 建队 / 入队 | 会话与队伍功能 | 登录态、每人限一队、邀请码入队可用 |
| **P3 提交与结果** | 提交页 + 结果详情 + 配额 | 提交流程闭环 | 提交→排队→结果轮询→终态展示可跑 |
| **P4（v2 延后）** | 管理端：提交总览 / 重测 / 封禁 / Stage 控制 / 公告 | 按 B2 = C 本版不做 | — |
| **P5（v2 延后）** | Stage 2 现场赛、榜单冻结、并列裁定 | 按 B2 = C 本版不做 | — |

### 1.3 契约策略（决策 B1 = C：沿用旧名）

**已定**：不引入 `/api/submission`、`/api/standings` 等新命名；只扩展 `/api/result/<id>`、`/api/leaderboard/<problem>` 的字段，真正的新功能（auth / team / problems）才加新端点。因前端整体重写且无外部消费者，无需兼容层或 deprecated 别名。

（被否：A 改名迁移、B 旧接口作别名。）

### 1.4 子项目拆分（决策 B2 = C：先砍范围）

**已定**：v1 只做"提交 + 排行榜 + 结果 + 最小登录"，管理端 / 公告 / Stage 2 延后。在此范围内仍按边界保留三块，但 v1 只交付最小集：

| 子项目 | v1 范围 | 依赖 |
|---|---|---|
| **S1 前端交互层** | 首页 / 赛题 / 排行榜 / 提交 / 结果 页面 + 视觉 token | 依赖 S2/S3 契约与 mock |
| **S2 身份与组队** | 最小注册登录 + User/Team 表 + 邀请码 | 独立，可先做 |
| **S3 评测与计分** | 修后端阻断 + verdict / details 字段 | 依赖评测口径 |

> 人力紧时，v1 可先交付 S1 + S3 阻断修复，登录先用"队名即提交"过渡。

### 1.5 前端落地约定

- 公共骨架 `templates/base.html`：两层导航 + 右侧栏插槽 + footer + 主题切换。
- 片段路由统一前缀 `/frag/`，返回 `text/html`；表单接口按 `HX-Request` 决定返回片段或 JSON（或按 M3 直接拆 `/frag/submit`）。
- 自定义 token 必须**映射到 Bootstrap 的 `--bs-*` 变量**（如 `--bs-primary: var(--brand-700)`），避免组件色与 token 两套。
- 主题切换：`data-bs-theme` 写在 `<html>`，用户显式选择存 `localStorage` 并覆盖 `prefers-color-scheme`。

## 四、验收与验证

**每页交付前必做（Playwright MCP）**：桌面 1440×900 与移动 390×844 各截图；检查 console 报错、network 4xx/5xx；深色模式截图。

- 冻结（Stage 2）后榜单拒绝写操作。

### 5.2 Verdict 状态机（建议默认）

```
pending ──► running ──┬─► accepted      (正确性通过 + 计分成功)
                      ├─► compile_error (编译失败)
                      ├─► timeout       (超时)
                      ├─► runtime_error (运行出错)
                      └─► invalid       (正确性未通过，一票否决)
```

- `wrong_answer` **并入 `invalid`**：本项目正确性一票否决，"答案错"即"成绩无效"，不再单列。
- 终态：`accepted` / `compile_error` / `timeout` / `runtime_error` / `invalid`。结果页轮询仅在非终态继续。

### 5.3 计分口径（已采用；真实赛道口径见 `docs/06` §2.4）

- 单题得分：`100 × (全场该题最优时间 / 本队该题时间)`；多数据集时先各自归一化再取平均（依据策划案 7.2）。
- 取当日最优：`队伍某题当日得分 = 当日所有有效提交中的最大值`。
- 总分：`总分 = 各题得分之和`（单题上限 100）。
- 正确性未过：不计入任何最优。
