## 一、功能介绍

### 1.1 功能概述

本方案定义「RISC-V AI 编译器挑战赛」线上评测平台（`riscv-ai-compiler-platform`）的**前端设计与实现规范**。平台面向华东师范大学全日制在读学生，承载 Stage 1 线上赛的报名、组队、提交、评测结果展示与排行榜公示。

前端由以下能力构成：

- **公共浏览**：赛事概览、三道赛题（`fwht` / `conv` / `spmv`）说明、Standings 排行榜、帮助 FAQ。
- **账号与组队**：个人账号注册/登录；队长建队生成邀请码，成员凭码入队（每队 1~3 人，每人限一队）。
- **提交与结果**：选择赛题 + 上传源码；评测进度与结果详情（verdict、分用例 cycles/指令数/得分）；今日提交配额（99 次/天）。
- **管理端**：提交总览、重测、封禁、Stage 控制/榜单冻结、发布公告。

前端**不是**独立 SPA，而是"服务端渲染 + 局部刷新"的轻量交互层：页面由 Flask + Jinja2 渲染，交互用 htmx 做局部替换、Alpine.js 做纯前端小状态，数据同时暴露干净的 REST API。

### 1.2 设计目标

- **信息密度优先**：沿用 Codeforces 的"表格 + 徽章 + 等宽数据"信息架构，让竞赛选手零学习成本。
- **SPA 手感、零构建链**：提交不整页跳转、排行榜自动刷新、结果页轮询，全部用 htmx 声明式实现，不引入 Node/React/Vite。
- **移动优先与可访问**：响应式到 390px；交互元素键盘可达、有可见 focus、带 `aria-label`。
- **与赛制规则严格对齐**：每队每日 99 次（每日 05:00 UTC+8 重置配额）、取历史最优（跨日累计）、正确性一票否决、分数为"相对全场最优"的百分制。
- **品牌一致**：采用 LLVM 官方图标的青蓝色调，规避商标风险（只取色、不直接用官方龙标）。
- **可独立演进**：前端通过 REST 契约与后端解耦，后端可替换评测实现而不影响界面。

## 二、设计规范

### 2.1 架构与实现路径（前后端分离边界）

采用 **htmx 优先**方案，分离边界划在"HTML 片段 / JSON API"层，而非"独立前端工程"层：

```
浏览器 ──(整页 GET)──────────────► Flask + Jinja2 ──► templates/*.html
       ──(htmx 局部请求 HX-Request)► Flask 片段路由 ──► fragments/*.html
       ──(JSON /api/*)───────────► Flask API 路由 ──► 数据库/评测队列
```

| 层 | 职责 | 技术 |
|---|---|---|
| 页面层 | 整页骨架、导航、首屏数据 | Jinja2 模板 |
| 交互层 | 局部刷新、轮询、表单提交 | htmx（CDN） |
| 本地状态 | 下拉/tab/弹窗/主题切换 | Alpine.js（CDN，仅局部） |
| 数据层 | 结构化数据消费 | `/api/*` JSON（REST） |

**约束**：htmx 与 Alpine 通过 CDN 引入并锁定版本，禁止引入任何构建工具。

### 2.2 信息架构与角色权限

**角色**：`访客` → `选手` → `队长` → `评委` → `管理员`（权限递增）。

| 能力 | 访客 | 选手 | 队长 | 管理员 |
|---|:--:|:--:|:--:|:--:|
| 浏览首页/赛题/排行榜 | ✅ | ✅ | ✅ | ✅ |
| 提交代码 | ❌ | ✅ | ✅ | ✅ |
| 建队/入队 | ❌ | ❌ | ✅ | — |
| 查看本队提交历史 | ❌ | ✅ | ✅ | ✅ |
| 重测/封禁/发公告/冻结榜单 | ❌ | ❌ | ❌ | ✅ |

**全局导航**（顶部两层）：

- 品牌条：风格化龙标 + 赛事名 + `Stage 1` 徽章 + 刷新倒计时 + 主题切换 + 登录态。
- 主菜单：`首页 | 赛题 | 排行榜 | 提交 | 我的队伍 | 帮助`；管理员多一项 `管理`。

**布局骨架**：桌面 = 主内容 + 右侧栏（公告 / 倒计时 / 快捷入口）；移动 = 单列堆叠。见附录 5.2 线框。

### 2.4 组件规范

#### 2.4.1 Verdict 徽章（一等状态；状态机见《实现策略与注意事项》5.2）

| 状态码 | 文案 | 语义 | 色 |
|---|---|---|---|
| `pending` / `running` | 排队中 / 评测中 | 处理中（带 spinner） | 灰 |
| `accepted` | 通过（得分 X） | 正确性通过 + 计分成功 | `--ok` 绿 |
| `compile_error` | 编译失败 | 源码无法编译 | `--err` 红 |
| `timeout` | 超时 | 超过评测时限 | `--warn-text` 琥珀 |
| `runtime_error` | 运行错误 | 运行期异常 | `--err` 红 |
| `invalid` | **正确性未通过** | 一票否决，成绩无效 | `--critical` 深红 `#900020` |

> `wrong_answer` 并入 `invalid`：本项目正确性一票否决，"答案错"即"成绩无效"，不再单列。

#### 2.4.2 Standings 表

列：`# | 队伍 | 总分 | <每题一列> | 提交次数 | 最后提交`。规则：

- **列渲染数据驱动**（决策 B3）：题目列表从 `/api/problems` 读取，当前为 3 题 = `fwht` / `conv` / `spmv`；改题数不需改前端。

- 总分列固定宽度、等宽字体、右对齐；各题分列可点击排序（htmx 局部重排或 Alpine）。
- 当前登录队伍所在行高亮。
- 支持 `stage=1|2` 与 `problem=all|fwht|conv|spmv` 查询参数。
- 空榜单显示"暂无有效提交 + 去提交"引导。

#### 2.4.3 今日配额组件

显示"今日已提交 12 / 99，下次刷新 05:00（剩余 3h12m）"，配额耗尽时禁用提交按钮并给出提示。

#### 2.4.4 结果分用例表

`用例 | 规模/配置 | cycles | 指令数 | 得分 | 状态`。正确性未过时，表格顶部置顶警告条并隐藏得分列（避免误导）。

#### 2.4.5 状态与反馈

所有异步操作有：加载态（spinner/骨架）、成功态、失败态（可操作文案）；错误不道歉、不空泛。空状态即行动入口。

#### 2.5.2 字体与排版

- 正文/标题：`system-ui, -apple-system, "Segoe UI", "Noto Sans SC", sans-serif`（零外部依赖）。
- 数据/编码：`ui-monospace, "JetBrains Mono", "Cascadia Code", monospace`（分数、cycles、指令数、源码、邀请码）。
- 字号阶梯：12 / 14 / 16 / 20 / 28 px；行高 1.5（正文）、1.3（表格）；正文行宽 < 80 字符。

#### 2.5.3 品牌与合规

- 只提取 LLVM 图标的**配色**用于界面；**不直接使用官方龙形商标**，如需使用须联系 `board@llvm.org` 取得授权。可使用自绘风格化龙形/几何图形作为占位品牌标记。

### 2.6 REST API 契约

**契约策略（决策 B1 = C：沿用旧名）**：不引入 `/api/submission`、`/api/standings` 等新命名，只**扩展现有接口字段**，真正的新功能才加新端点。

| 方法 | 路径 | 状态 | 说明 |
|---|---|---|---|
| POST | `/api/submit` | 现有 | 提交（`team,problem,code`）→ `{submission_id}`（需修现有 500 bug） |
| GET | `/api/result/<id>` | 现有 | 结果详情 → `{status,verdict,score,details}`（`to_dict` 需补字段） |
| GET | `/api/leaderboard/<problem>` | 现有 | 榜单 → `[row]`（建议扩展 `stage` 查询参数） |
| GET | `/api/problems` | 新增 | 赛题元数据（3 题，供榜单列数据驱动） |
| GET | `/api/submissions` | 新增 | 提交列表（`team,problem,page`） |
| POST | `/api/auth/register` · `/api/auth/login` · `/api/auth/logout` | 新增 | v1 最小登录 |
| GET | `/api/me` | 新增 | 当前用户/队伍/配额 |
| POST | `/api/team` · `/api/team/join` | 新增 | 建队（邀请码）/ 入队 |

> 管理端与公告端点（`/api/admin/*`、`/api/announcements`）按 **B2 = C** 延后至 v2，本版不实现。

**HTML 片段路由（htmx 专用，返回 `text/html`）**：

| 路径 | 用途 | 触发 |
|---|---|---|
| `GET /frag/leaderboard/<problem>` | 榜单表体 | `hx-trigger="load, every 15s"` |
| `GET /frag/result/<id>` | 结果卡片 | 轮询 `every 2s` 直到终态 |
| `GET /frag/quota` | 今日配额 | 提交后 / 每 60s |
| `POST /api/submit` | 提交反馈 | 请求头含 `HX-Request` 时返回片段，否则 JSON（M3：亦可拆 `/frag/submit`） |

**结果字段扩展**：`models.py` 的 `to_dict()` 需补齐 `details`、`updated_at`（`verdict` 于评测改造时加入），否则结果页无数据（现状缺陷）。

### 2.7 约束规则

- 布局用 Flex/Grid 与 Bootstrap 栅格，**禁止用绝对定位搭结构**。
- 交互元素必须有 `aria-label`、键盘可达、可见 focus 样式。
- 术语统一：`fwht` / `conv` / `spmv`，与赛题一致；文案用户视角、动词开头。
- 深色模式与浅色模式视觉等价，不允许某模式缺失。
- 不引入 Tailwind / React / Next / shadcn / 构建工具。

### 2.8 计分与刷新语义（口径见《实现策略与注意事项》5.3；H1/H2 已决）

- **分数语义**：单题得分 = 100 ×（全场该题最优时间 / 本队该题时间）；多数据集先各自归一化再取平均（策划案 7.2）。
- **历史最优**：队伍某题得分 = **全部有效提交中的最大值**（跨日累计）。
- **总分合成**：默认 `总分 = 各题得分之和`（随 B3 = 3 题；若改为按题独立排名则只展示各题分）。
- **刷新语义**：排行榜**实时展示**，按跨日累计的历史最优排名；每日 **05:00（UTC+8）** 只重置提交配额，不清零成绩、不定格名次。
- **并列裁定**：Stage 2 按"提交时间更早者优先，其次 Stage 1 历史最优更优者"（策划案 6.5）。

## 三、测试设计

前端验证以 **Playwright MCP 真机截图 + console/network 检查**为准（不能只看代码）。以下每个用例给出输入、预期输出与验证点。

### 测试用例 1：提交流程（含配额与错误反馈）

- **输入**：登录后进入 `/submit`，选择 `fwht`，上传合法 `.py`（≤10MB），点击"提交评测"。
- **预期输出**：页面**不整页跳转**；出现提交中 spinner → 成功后局部显示"评测 ID: N（查看结果）"，配额由 `x/99` 减 1；若配额为 0，提交按钮禁用并提示刷新时间。
- **验证点**：`POST /api/submit` 返回 2xx；无 500；`/frag/quota` 数字更新；按钮 `aria-label` 与 disabled 态正确。

### 测试用例 2：排行榜（切题 / Stage / 自动刷新）

- **输入**：访问 `/standings`；依次点击 `fwht`、`conv`、`spmv` 与 `Stage 1/2` 切换；静置 30s。
- **预期输出**：表格仅局部刷新；列固定为 `#/队伍/总分/三题分/提交次数/最后提交`；本队行高亮；无提交时显示空状态引导。
- **验证点**：15s 轮询触发 `GET /frag/standings`；切换参数后 `problem/stage` 正确；表格不出现横向溢出（1440 与 390 两视口）。

### 测试用例 3：结果详情（正确性一票否决）

- **输入**：打开一个"正确性未通过"的 `/submission/<id>`，以及一个 `accepted` 的提交。
- **预期输出**：前者置顶深红警告"正确性未通过，成绩无效"且不显示得分；后者绿色"通过（得分 X）"并展示分用例表（cycles/指令数/得分）。
- **验证点**：`details` 字段非空、verdict 映射正确；轮询在终态停止；`invalid` 状态视觉与 `wrong_answer` 明确区分。

### 测试用例 4：移动端 + 深色模式 + 可访问性

- **输入**：390×844 视口；系统深色；仅用键盘 Tab 操作主菜单与提交表单。
- **预期输出**：单列堆叠无横向滚动；深色下 token 全部生效、对比度可读；所有可聚焦元素有可见 focus 环。
- **验证点**：`prefers-color-scheme: dark` 截图无浅色残留；无 console 报错、无 404 资源（含 CDN 的 htmx/Alpine/Bootstrap）。

## 四、修改模块与实现步骤

### 4.1 涉及文件

- **模板**：`templates/base.html`（新增，公共骨架/导航/主题）、`index.html`、`problems.html`、`standings.html`、`help.html`、`login.html`/`register.html`、`team.html`、`submit.html`、`submission.html`、`admin.html`、`error.html`。
- **片段模板**：`templates/fragments/standings.html`、`submission_status.html`、`quota.html`、`submissions_table.html`。
- **静态资源**：`static/style.css`（token + 组件样式）、`static/app.js`（极少量 Alpine/工具函数）。
- **后端对接**：`app.py`（新增页面/片段/API 路由）、`models.py`（`to_dict` 补字段、新增 User/Team/Announcement 表）、`tasks.py`/`evaluator.py`（产出 verdict/details）。

> 注：新增 User/Team/Announcement 等模型属后端范围，前端方案假设其存在并按 2.6 契约消费；实际路径可能随后端实现调整。

### 4.2 逐步实现步骤

1. **设计 token 落地**：在 `static/style.css` 定义 2.5 的 CSS 变量与浅/深色两套值，用 `data-bs-theme` 切换。
2. **搭建 `base.html`**：顶部两层导航、右侧栏插槽、footer；移动端汉堡菜单（Alpine 控制）。
3. **引入 htmx 与 Alpine**：CDN 锁定版本；在 `base.html` 挂载；约定片段路由前缀 `/frag/`。
4. **逐页实现**：先公共页（首页/赛题/排行榜），再账号与队伍，再提交与结果，最后管理端。
5. **接入 API**：按 2.6 契约对接；提交接口做"`HX-Request` 返回片段 / 否则 JSON"双态。
6. **自检闭环**：每完成一页，起 `python3 app.py`，用 Playwright MCP 在桌面 1440×900 与移动 390×844 截图、查 console/network，修完再下一页。
